# Optional High-Security Camera View

**Status:** Approved hackathon design, 2026-09-26. Camera checks are browser-reported viewing controls, not identity verification or proof of misconduct.

The sender may require webcam checks separately for each new recipient link. Existing links default to off; a link's setting is fixed when sent. The recipient sees the requirement before granting camera permission. A required link does not download or decrypt a file until a local YuNet face detector reports exactly one face in three consecutive checks. YuNet detects faces only; a separate browser rules engine interprets face counts, track events, and frame freshness. The same camera session continues across file switches. A small rounded self-preview sits inside the fullscreen document root, so the recipient can see the live camera image throughout viewing. Camera frames and video never leave the browser; no microphone is requested.

The rules engine samples around four times per second. It tolerates a missing face for less than two seconds, blurs and covers the document at two seconds, and locks at four seconds. Two or more faces for two seconds, dark/obscured video for about 1.5 seconds, or no advancing video frames for about 1.5 seconds lock the viewer. A camera track ending locks immediately; mute covers immediately while the short stall timer runs. A still-looking scene alone is not evidence of a frozen camera. Hidden tabs and fullscreen exit remain covered under the existing viewer policy. A lock removes the displayed page and drops decrypted file references; the recipient must pass three fresh one-face checks and reopen the file. Stopping or leaving the share stops the stream and worker. Camera or model failure never falls back to an unmarked or unverified view.

The `shares` row gains `camera_required` with a false default. Share creation accepts one boolean per recipient and cannot change an existing link's value. Authorized access responses include the boolean. Browser-reported events use the existing access-event endpoint with a strict event allowlist plus a session UUID and optional duration. Only state transitions are logged: `FACE_VERIFIED`, `FACE_MISSING`, `MULTIPLE_FACES`, `CAMERA_OBSCURED`, `CAMERA_STALLED`, `CAMERA_LOST`, `CAMERA_RESTORED`, `VIEWER_BLURRED`, `VIEWER_LOCKED`, and `VIEWER_UNLOCKED`. No frame, image, video, face embedding, or behavioral score is accepted. An owner-only, bounded History view shows these with the label “Reported by recipient browser.” Events older than 30 days are hidden and removed by a protected daily scheduled route. The UI clearly says these events cannot prove who used the browser.

YuNet is pinned to OpenCV's `face_detection_yunet_2026may.onnx` by SHA-256 and runs locally in an ONNX Runtime Web worker, attempting WebGPU with WASM fallback. Runtime assets come from the exact locked ONNX Runtime Web version; failure to load either blocks required viewing. The existing encrypted-file and experimental TrustMark boundaries stay intact.

Acceptance checks cover per-recipient settings and old-link defaults, authorized APIs, permission denial, model failure, face/camera timing, recovery, fullscreen preview, file switches, transition-only telemetry, absence of media in network payloads, and 30-day purge. Validate the migration only on a disposable database. Deployment needs a configured `CRON_SECRET`; no deployment or shared-database migration is implied by this design.
